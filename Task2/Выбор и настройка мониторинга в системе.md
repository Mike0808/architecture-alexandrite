## Мотивация
Без систем наблюдаемости нельзя отслеживать, что происходит в системе. Нет информации о сбоях, нет возможности понять причины падений, нельзя проанализировать производительность или отследить утечки.
Это своего рода система отслеживания жизнедеятельности продукта без которой любой инцидент может быть фатальным.
## Выбор подхода к мониторингу
### RED
Идеально подходит для микросервисов и HTTP-интерфейсов.
**Поэтому:**
- Онлайн-магазин, 
- CRM бэкенд, 
- MES бэкенд, 
- API Gateway
#### Мониторим:
Rate — количество запросов в секунду (RPS).
Errors — процент ошибок (HTTP 5xx, 4xx, исключения).
Duration — время обработки запроса (p50, p90, p99).
- Онлайн-магазин количество запросов (RPS) на создание заказа
- CRM количество запросов (RPS) на на создание заказа
- MES количество запросов (RPS) на расчёт стоимости, Duration расчёта (даже если асинхронный — фиксируем время от старта до события PRICE_CALCULATED).
- API Gateway: количество запросов (RPS) от внешних продавцов, количество ошибок авторизации.
### USE
Позволяет оценить и предотвратить перегрузку ресурсов.
#### Мониторим:
Utilization — загрузка ресурса (CPU, RAM, дисковый I/O, сетевой трафик).
Saturation — очередь запросов (например, load average, queue depth, unacknowledged messages).
Errors — аппаратные или системные ошибки (disk failure, network drops).
**Поэтому:**
- Серверы (EC2 / Kubernetes nodes)
- Базы данных (PostgreSQL)
- Очереди (RabbitMQ)
**PostgreSQL:**
- Utilization: CPU, I/O, connections, pages, transactions.
- Saturation: waiting backends, long-running queries, load avearge, locks
- Errors: failed connections, replication lag.
**RabbitMQ:**
- Utilization: потребление памяти, диска.
- Saturation: размер очередей, unacknowledged messages.
- Errors: сбои соединения, отказы потребителей.
**Kubernetes nodes:**
- Utilization: CPU, memory.
- Saturation: pod scheduling delays, throttling
- Errors: Kubernetes fails

## План действий на 6 месяцев (по кварталам)
Построить **стабильную, наблюдаемую, отказоустойчивую и масштабируемую** систему, способную:
- Выдерживать рост нагрузки (100+ заказов в месяц),
- Обеспечивать прозрачность работы,
- Снижать количество просроченных заказов и жалоб,
- Поддерживать внешние интеграции (API для партнёров).
  
### Месяцы 1–2: Основа стабильности и видимости
#### Цель: сделать систему **наблюдаемой** и **защищённой от перегрузки**
#### Ключевые инициативы:

##### 1. **Внедрение системы наблюдаемости (MVP)**
- Развернуть **Loki + Promtail** для централизованного логирования.
- Настроить **Prometheus + Grafana** для метрик.
- Добавить **OpenTelemetry** в Java- и C#-сервисы (начать с онлайн-магазина и CRM).
- Настроить дашборды:
  - RPS, ошибки, latency (RED).
  - CPU, RAM, queue depth (USE).
  - Latency и saturation API (Golden Signals).

> **Результат:** команда видит, где падают сервисы, сколько длится расчёт, какие очереди растут.
**Риски:** Нестабильная работа монолита при внедрении агентов: OpenTelemetry может повлиять на производительность, особенно в C#-сервисе (MES).

##### 2. Защита внешнего API
- Развернуть **Yandex API Gateway** (или Kong).
- Добавить:
  - **API keys** для партнёров.
  - **Rate limiting** (100 запросов/мин на клиента).
  - **Аутентификацию** (JWT или ключи).
- Внедрить **кэширование ответов** для `/calculate-price` (если модель повторяется).
- Настроить **мониторинг трафика и ошибок**.

> **Результат:** прекращается "лавина" запросов, восстанавливается доверие с партнёрами.
**Риски:** Временная недоступность API для партнёров во время миграции. Старые клиенты не передают API keys. Жёсткие лимиты могут привести к тому, что легальные запросы блокируются, вызывая недовольство.
---

#### 3. **Начало горизонтального масштабирования**
- Перевести **онлайн-магазин** в Docker-контейнеры.
- Развернуть **базовый Kubernetes-кластер** (Yandex Managed Kubernetes).
- Запустить онлайн-магазин в 2+ репликах за **балансировщиком нагрузки**.
- Настроить **health checks** и **liveness probes**.

> **Результат:** устранён SPOF для онлайн-магазина.
**Риски:** Сбои при миграции: сервис временно недоступен.
Недостаток экспертизы в Kubernetes: ошибка в конфигурации.
Несовместимость с текущим CI/CD: ручной деплой не работает с кластером.
---

### **Месяцы 3–4: Укрепление инфраструктуры и производительности**

#### Цель: повысить **производительность**, **надёжность** и **отказоустойчивость**

##### 4. **Оптимизация работы с БД**
- Внедрить **read replicas** для PostgreSQL (CRM и MES).
- Настроить **PgBouncer** для connection pooling.
- Настроить **мониторинг долгих запросов**.

> **Результат:** дашборд в MES начинает загружаться быстрее.
**Риски:** Задержка репликации: оператор видит устаревшие данные.
Перегрузка primary-узла при записи.
Недостаток памяти на репликах.

##### 5. **Кеширование критических данных**
- Развернуть **Redis** (Yandex Managed Redis).
- Кэшировать:
  - Результаты расчёта стоимости (по hash 3D-модели + материал).
  - Список заказов (с TTL 30 сек).
  - Профили пользователей и справочники (материалы, цены).
- Внедрить **cache invalidation** при обновлении данных.

> **Результат:** сокращение времени расчёта на 70% для повторяющихся моделей.
**Риски:** Старение данных: кэш не обновляется при изменениях.
Коллизии хешей: разные модели дают одинаковый хеш.
Исчерпание памяти в Redis.

##### 6. **Асинхронизация расчёта стоимости в MES**
- Ввести статус `CALCULATING`.
- Перенести расчёт в **background job** (например, через Hangfire или RabbitMQ + worker).
- При старте расчёта — отправлять событие `PriceCalculationStarted`.
- При завершении — `PriceCalculated` → обновляет заказ и уведомляет CRM.
- Добавить **ограничение на параллельные расчёты** (backpressure).

> **Результат:** пользователь видит статус, система не "зависает".
**Риски:** Потеря задач: worker упал, а задача не вернулась в очередь.
Накопление в очереди: расчёты не успевают обрабатываться.
Дублирование расчётов: один заказ запущен дважды.

### **Месяцы 5–6: Повышение отказоустойчивости и гибкости**

#### Цель: сделать систему **самоисцеляющейся**, **слабосвязанной** и **готовой к росту**

##### 7. **Улучшение интеграции через RabbitMQ**
- Настроить **Dead Letter Queues (DLQ)**.
- Реализовать **retry с экспоненциальной задержкой** (в потребителях).
- Добавить **idempotency keys** для сообщений (чтобы избежать дублей).
- Внедрить **мониторинг очередей** (размер, unacked messages).

> **Результат:** меньше потерянных заказов, выше надёжность.
**Риски:** Сложность диагностики: трудно понять, где "застряло" сообщение.
Рост DLQ: слишком много ошибок — система не справляется.
Несовместимость потребителей: старые сервисы не поддерживают retry.

##### 8. **Автоматизация CI/CD**
- Настроить **GitLab CI / GitHub Actions**.
- Автоматический деплой:
  - В `dev` — после мержа.
  - В `release` — после ручного подтверждения.
  - В `prod` — после тестирования и approval.
- Внедрить **blue-green deployment** для онлайн-магазина и CRM.

> **Результат:** меньше ошибок при релизах, быстрый rollback.
**Риски:** Ошибки в pipeline - разрушительный деплой.
Недостаток тестов: автоматизация разворачивает битый код.
Сопротивление команды: привыкли к ручным деплоям.

#### 9. **Начало перехода к event-driven архитектуре**
- Определить ключевые события:
  - `OrderSubmitted`, `PriceCalculated`, `ManufacturingStarted`, `Shipped`.
- Настроить **публикацию событий** в RabbitMQ (или начать миграцию на Kafka).
- CRM и MES начинают **подписываться** на события, а не опрашивать друг друга.
- Ввести **event schema registry** (простой JSON-документ).

> **Результат:** снижена связанность, проще добавлять новые сервисы.
**Риски:** Потеря событий: нет durability, сбой брокера.
Несогласованность схем: разные версии события.
Сложность отладки распределённого потока.

#### 10. **Мониторинг и алертинг**
- Настроить **Alertmanager**:
  - Алерты при:
    - Duration > 30 сек (p99).
    - Ошибки > 5%.
    - CPU > 80% (5 мин).
    - Очередь > 100 сообщений.
- Настроить **уведомления** в Telegram/Slack.
- Создать **SLO/SLI** для ключевых процессов:
  - Расчёт стоимости: 95% — за 5 мин.
  - Обработка заказа: 90% — за 3 недели.

> **Результат:** команда реагирует до того, как клиенты начнут жаловаться.
**Риски:** Ложные алерты: "шум" - команда игнорирует оповещения.
Нет действия по алерту: неясно, что делать.
Недостаток контекста: алерт без логов или трейса.

### №1. Number of dead-letter-exchange letters in RabbitMQ

#### Что измеряет:
Количество сообщений, которые **не удалось обработать** и были перемещены в **Dead Letter Exchange (DLX)**.

#### Пороговое значение:
> **> 5 сообщений за 5 минут**

#### Почему именно это значение:
- Наличие **любых** DLQ-сообщений — уже **сигнал тревоги**.
- > 5 за 5 минут — признак **системной проблемы**, а не единичного сбоя.

#### Что должно происходить при превышении:
1.  **Алерт в мессенджер** (высокий приоритет)
2.  **Уведомление ответственного разработчика** (через email)
3. **Автоматическое создание тикета в TaskManager**:
   - Тема: `DLQ backlog detected: {count} messages`
   - Ссылка на инструмент просмотра сообщений (например, RabbitMQ Management UI)
4.  **Запуск диагностики**:
    Например приложение запрашивающее последние сообщения и проверяющее их на достоверность согласно установленным правилам качества данных
5.  **Проверка потребителей**: диагностика health state

> **Цель**: не допустить накопления "мёртвых" сообщений, которые могут означать потерю заказов.

### **№2. Number of message in flight in RabbitMQ**

#### Что измеряет:
Количество сообщений, которые **уже взяты потребителем в обработку**, но **ещё не подтверждены (acknowledged)**.

### Пороговое значение:
> **> 20 сообщений в полёте (in flight) на одну очередь**

### Почему именно это значение:
- При нормальной работе — сообщения обрабатываются быстро (секунды).
- Если > 20 — потребитель **не справляется**:
  - Перегружен,
  - Завис,
  - Не отправляет `ack`.
- Риск: при падении потребителя — сообщения **вернутся в очередь**, возможны **дубли**.

### Что должно происходить при превышении:
1.  **Алерт в мессенджер** (средний приоритет)
2.  **Уведомление ответственного разработчика** (через email)
3. **Диагностика потребителей**:
   - health state
   - Есть ли ошибки в логах?
   - Нагрузка на CPU/память потребителя
4. **Автомасштабирование потребителей** (если возможно):
   - Добавить ещё один экземпляр воркера
5. **Автоматическое создание тикета в TaskManager**: `High in-flight messages in {queue}`
6. **Ручной/автоматический рестарт зависшего потребителя** (если не отвечает)

### Что измеряют:
Количество **одновременно активных сессий**
В контексте насыщенности — будем считать, что **сессии требуют ресурсов на сервере** (память, потоки, соединения).

### Пороговое значение:

### Почему именно это значение:
- Предположим, что каждый инстанс рассчитан на **100 активных пользователей**.
- При > 100:
  - Риск исчерпания пула потоков,
  - Рост потребления памяти,
  - Замедление отклика.
- Это **прямой путь к отказу сервиса**.

### Что должно происходить при превышении:
1.  **Алерт в мессенджер** (низкий приоритет, если рост плавный; высокий — если резкий)
2. **Автомасштабирование потребителей** (если возможно):
   - Цель: до 100 сессий на инстанс
3. **Проверка источника роста**.
4. **Автоматическое создание тикета в TaskManager**: `Session saturation on {service}`
5. **Оповещение инфраструктурного специалиста**: если масштабирование не помогает
