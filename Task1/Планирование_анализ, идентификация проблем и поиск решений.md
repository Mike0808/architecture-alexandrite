### Cуществующие и потенциальные проблемные места с приоритезацией от высшего к низшему
Для приоритезации был выбран подход выделения внешнего контура проблем которые влияют на отслеживание работоспособности системы в целом - это самые приоритетные задачи и внутреняя архитектура систем которые увеличивают гибкость отказоустойчивость продукта. Также принято во внимание сложность реализации рекомендованных изменений.
**1.  Проблема** Не настроен ни один из компонентов "Наблюдаемости", что делает систему трудно обслуживаемой и неконтролируемой.
**Рекомендации**
Добавить системы: централизованного логирования, распределенного трейсинга и мониторинга метрик
**Объяснение приоритета**
Без систем наблюдаемости нельзя отслеживать, что происходит в системе. Нет информации о сбоях, нет возможности понять причины падений, нельзя проанализировать производительность или отследить утечки.

**2. Проблема** Открытая API MES без ограничений количества запросов и размеров сообщений, так же не прослеживается механизм авторизации, делает систему еще более уязвимой к второстепенным нагрузкам
**Рекомендации**
Ввести стратегию CircuitBreaker со стороны потребителей.
Ввести ограничение на количество запросов
Добавить API Gateway с аутентификацией и авторизацией
**Объяснение приоритета**
Отсутствие защиты API делает систему уязвимой к:
- DDoS (спам запросы)
- Атакам (несанкционированный доступ)
- Перегрузке сервисов
  
**3. Проблема** Единычные инстансы БД, без репликации и шардирования могут привести к замедлению ответов на запросы, либо полной отказе БД
**Рекомендации**
Разделить БД относительно бизнес-сущностей
Добавить шардирование и read реплики. 
Давить инструмент для сосздания connect pooling для postgresql например PgBouncer
**Объяснение приоритета**
База данных — узкое место и главный SPOF. Если она упадёт — вся система не работает.
Монолитные БД не масштабируются, медленно отвечают при росте данных.
Нужно устранить до роста нагрузки.

**4. Проблема:** Отсутствует горизонтальное масштабирование. Все сервисы запущены в единственном экщемпляре - Single Point of Failure (в случае сбоя полный отказ системы), вследствии слишком уязвима при высоких нагрузках.  
**Рекомендации**
Развернуть кластеры (например, Kubernetes или ECS) с несколькими экземплярами каждого сервиса.
Использовать load balancer и auto-scaling.
**Объяснение приоритета**
Система с одним экземпляром сервисов не может выдержать нагрузку и падает целиком при любом сбое. Это фундаментальная уязвимость.Нет стабильности даже при нормальном режиме нагрузки без пиковых режимов

**5. Проблема** Нет автоматизации CI/CD в продакшн и в релиз. Увеличивается риск ошибки. Усложняется процедура rollback
**Рекомендации**
ввести автоматизацию CI/CD
применить B/G deploy или canary deploy
**Объяснение приоритета**
Ручные релизы — источник ошибок, медленные rollback, высокий риск возникновение инцидентов с высоким приоритетом.

**6. Проблема** Нет праработки кеширующего слоя при работе с MES, CRM, онлайн-магазина
**Рекомендации**
Доработать кеширующий слой (Read/Write Through) для
MES: результаты расчетов стоимости
     Список заказов
CRM: Пользователи
    Справочники и конфигурации изделий
Online-shop: статусы, заказы
**Объяснение приоритета**
Кеширование — самый быстрый способ улучшить производительность. Особенно для:
- Расчётов в MES
- Справочников и статусов CRM
- Заказов в онлайн-магазине
Снижает нагрузку на БД и сервисы, ускоряет ответы. Высокая отдача при низкой сложности. 

**7. Проблема** Высокая нагрузка на монолит MES без возможности ее управления и его низкая производилтельность. Нет возможности отследить статус заказа.
**Рекомендации**
Использовать стратегию backpressure - асинхронный расчёт с обратной связью с возможностью кеширования результатов и регулирования потока задач с применением буфера задач на базе NAT.
Добавить статус CALCULATING. Возможно проработка разделения монолита на сервисы согласно бизнес задачам.
**Объяснение приоритета**
Уже после базовой стабильности можно оптимизировать внутренние процессы. 
Также частично решается кешированием.

**8. Проблема** RabbitMQ плохо подходит для горизонтального масштабирования. Нет гарантированной доставки, нет обработчика ошибок и механизмов повтора с вариативной задержкой, нет возмоности DQL.
**Рекомендации**
Добавить dead-letter queues (DLQ).
Реализовать retry с экспоненциальной задержкой.
Проработать возможность перехода на Kafka
**Объяснение приоритета**
RabbitMQ — не фатален, но:
- Нет DLQ → потеря сообщений
- Нет retry с backoff → сбои при временных ошибках
Улучшает надёжность, но пока не критичен, если нет массовых потерь, опять же без мониторинга не установить.
При переходе на Kafka приоритет может быть понижен так как требует массового изменения
**9. Проблема** Высокая связанность компонентов делает систему очень неустойчивой и зависимой друг от друга
**Рекомендации**
Перейти на event-driven архитектуру с использованием Kafka
**Объяснение приоритета**
Event-driven архитектура — это стратегическое улучшение, но:
- Требует перепроектирования системы
- Эффективно только после базовой стабильности
Это глобальное улучшение продукта в целом, что на первых этапах может подождать пока не установится базовая стабильность системы
**10. Проблема** Нет стратегии отказоустойчивости при интеграциях (circuit breaker)
**Рекомендации**
В местах интеграции применить варианты CR, retry на стооне продукта
**Объяснение приоритета**
Circuit Breaker — важен, но работает только при наличии мониторинга и сети. устанавливаться должен также на продуктах интегрирующих данный продукт.
Частично решается с помощью API Gateway и через Наблюдаемость так как картина работы продукта становится более прозрачной

## Ответы на вопросы
Какой вы видите целевую архитектуру через полгода?
Через полгода я вижу стабильную, наблюдаемую, масштабируемую и отказоустойчивую систему частично построенную на принципах облачной нативной архитектуры (cloud-native) 
За полгода можно сплаировать частичное выполнение первых 4 пунктов по приоритету сверху полное выполнение займет в районе  1 года
Если бы у вас была возможность выполнить только три пункта из списка инициатив в ближайшие полгода, что бы вы выбрали и почему? Не обязательно добавлять в список только эпики. Вы можете включить в план как крупные изменения, так и локальные задачи.
1. Обязательно реализовать пункт с наблюдаемостью займет в районе 3-4 мес в зависимости от выбранного пути применениия при реализации логирования, трейсинга и мониторонига так как в зависимости от ресурсной базы как специалистов так и технического комплекса можно выйти к развилке.
2. Перейти на API Gateway + rate limiting + аутентификация для интеграции
3. Горизонтальное масштабирование сервисов + отказ от single-инстансов.
